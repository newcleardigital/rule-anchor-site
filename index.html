The problem

AI agents now write much of the code.

In regulated software (fintech, insurance, anything bound by a law, standard or contract), “the AI wrote it and it looks right” won’t pass an audit.

Teams must show that each rule from the outside authority became code, was tested, and was checked by a named person.

Today that proof sits in spreadsheets, Jira tickets and memory.

AI agents don’t keep it, and they drift: session 12 quietly contradicts session 3.

How it works

They give the AI the rules. We make it follow them.

Requirements tools now hand your specification to the AI as context. Context can be skipped. Anchored sits in the agent's working loop and in your build, so a broken rule is caught before it goes any further.

01

Caught while the AI types

When the agent saves a file, the check runs. A number from the rulebook typed into the code, a requirement ID that does not exist, a banned name: each is named with its file and line, and the agent fixes it in the same turn. Your build runs the same checks again, and a rule without a passing test fails it.

02

The AI cannot approve itself

A reading of a rule counts only when a named person signs it, in their own terminal, in a commit that changes nothing else. The agent is blocked from signing or rewording a signed rule, and CI checks every sign-off against the approver list. The record shows it when an approver also changed the code.

The method

Four steps, one of them human.

The part of your code a specification governs, usually 15 to 25 percent, is anchored to it; everything else is built the way you build it today.

  1. Bring in your specification

    The agent drafts one numbered requirement per rule, each pointing to the paragraph it came from, all marked unapproved, with every unclear point listed.

  2. A person approves each one

    Your domain expert decides what each requirement means. Only the people you name can approve.

  3. Every change is checked

    As the agent writes, and again in your build. Each requirement needs its own passing test.

  4. Export the proof

    One command produces the traceability record for the current code version, ready for review.

Limits

What it does not do.

Your experts decide what the rules mean. Anchored gives them evidence they can check.

It does not interpret your rules

If your expert approves a reading, the code follows that reading, and the record shows who approved it.

It does not give legal advice

It proves that the code does what the approved requirements say. What a rule means is decided by your people.

Can we try it before paying?

Yes. Anchored Scan and Anchored Lite are free and show how the checks work on your own code. The paid toolkit adds the rule catalogue, the approval lock, a test per rule and the evidence export; the sample change record shows what you get. We already use Jira, Confluence or ServiceNow.

Keep them. They hold tickets and change requests; Anchored works where the code is written: it catches untraced changes as they are saved and fails the build on any that remain. Its evidence exports as a CSV you can attach to those records.

We don't use AI on that part of our code yet.

Then this is the easiest time to start: setup is simplest before the first AI-written line, and the record is complete from day one.

Which rulebooks does it work with?

Any written document your software must follow: a product specification, a contract, pricing and consumer rules, or payment and billing rules.

What do we need?

For Anchored: Claude Code, a GitHub repository and Python 3 in your CI. The free Scan needs only GitHub. The checks work with TypeScript, Python, Java, Kotlin, C#, Go, Rust and more.

Does our code leave our servers?

No. The checks run in your repository and your build. Nothing is sent to us.
